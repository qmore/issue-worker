# LLM setup guide

This document is written for an LLM / coding agent that has been asked to configure `qmore/issue-worker` on a trusted self-hosted machine.

The goal is to make setup deterministic and to prevent an agent from improvising around credentials or runner registration.

## Mission

Configure a private GitHub repository so that a maintainer can add the label `codex:run` to an Issue and have the Issue implemented by the local Codex CLI on a self-hosted runner, producing a branch and pull request.

## Non-negotiable safety rules

1. Never request that a user paste a GitHub PAT, Codex `auth.json`, refresh token, API key, SSH private key, or password into chat.
2. Never commit credentials or runner registration tokens to Git.
3. Never place credentials in Issue text, workflow YAML, README files, logs, or artifacts.
4. Use only private target repositories for self-hosted execution unless the user explicitly designs a separate hardened disposable environment.
5. Do not bypass Codex sandboxing to make setup easier.
6. Do not use `--dangerously-bypass-approvals-and-sandbox`, `--yolo`, or `danger-full-access` as a setup shortcut.
7. Do not configure the workflow to trigger on arbitrary Issue text. Use an explicit maintainer-applied label.
8. Do not add broad GitHub permissions beyond `contents: write`, `issues: write`, and `pull-requests: write` unless the target project has a separately justified requirement.
9. The workflow must have a timeout.
10. If a step requires a short-lived token generated by GitHub's UI, instruct the human to open the relevant GitHub page and use the generated command. Do not invent a token.

## Inputs the agent should establish

Resolve these values before modifying the project:

```text
TARGET_REPO        = owner/repository
RUNNER_SCOPE       = repository | organization
RUNNER_LABEL       = codex            (recommended default)
BASE_BRANCH        = empty/default or explicit branch
RUNNER_OS          = macOS | Linux
RUNNER_USER        = OS account running GitHub Actions
ISSUE_WORKER_REF   = qmore/issue-worker@main during setup; pin for production
```

If the user has not selected repository vs Organization runner scope:

- choose **repository** for one private repository
- choose **organization** when multiple repositories in one GitHub Organization should share a runner

Do not confuse runner scope with the location of `qmore/issue-worker`. `issue-worker` is a Composite Action. The caller repository chooses `runs-on`.

## Phase A — inspect the machine

Run read-only checks first:

```bash
uname -a
whoami
pwd
git --version || true
gh --version || true
codex --version || true
command -v git || true
command -v gh || true
command -v codex || true
```

On macOS also check:

```bash
xcode-select -p || true
```

Do not install anything until the missing prerequisites are known.

## Phase B — install prerequisites

### macOS

If Xcode Command Line Tools are missing, instruct/run:

```bash
xcode-select --install
```

This opens an Apple installer UI and may require human interaction. Do not loop or repeatedly invoke it.

If Homebrew is already installed and `gh` is missing:

```bash
brew install gh
```

If Homebrew is not installed, either use GitHub's documented alternative installation path or ask the user whether Homebrew should be installed. Do not silently add a package manager to a managed machine.

Install Codex CLI using the current OpenAI installer:

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

Then verify:

```bash
codex --version
```

### Linux

Install `git` and `gh` through the user's approved package-management process, then install Codex:

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

Verify all three:

```bash
git --version
gh --version
codex --version
```

## Phase C — verify Codex authentication

First try a non-mutating non-interactive run:

```bash
codex exec \
  --sandbox read-only \
  --ask-for-approval never \
  --ephemeral \
  "Reply with the single word OK."
```

Expected: command exits successfully and prints an OK-like final response.

If authentication is not configured:

```bash
codex
```

Have the human complete the supported sign-in flow.

If the runner will operate as a persistent service and GUI/keychain authentication does not survive service execution, follow OpenAI's current trusted CI/CD guidance:

https://developers.openai.com/codex/auth/ci-cd-auth

Never print `auth.json`. Never read it into model context. If only file existence/permissions need checking, use metadata commands such as:

```bash
AUTH_FILE="${CODEX_HOME:-$HOME/.codex}/auth.json"
if [ -f "$AUTH_FILE" ]; then
  ls -l "$AUTH_FILE"
fi
```

Do not `cat`, `jq`, or otherwise expose token contents unless a human administrator explicitly performs that inspection outside model-visible logs.

## Phase D — register the self-hosted runner

This phase requires GitHub-generated commands.

### Repository scope

Human navigation:

```text
TARGET_REPO -> Settings -> Actions -> Runners -> New self-hosted runner
```

### Organization scope

Human navigation:

```text
Organization -> Settings -> Actions -> Runners -> New runner
```

Select the correct OS/architecture. GitHub will generate download/configuration commands containing a short-lived registration token.

The LLM may execute the generated commands if they are supplied through a secure local terminal context, but must not copy the registration token into repository files or chat summaries.

Recommended runner label:

```text
codex
```

If the generated `config.sh` command does not already include the desired label, use GitHub's runner settings to add `codex` after registration.

Acceptance check: GitHub shows the runner as **Idle/Online**, or local runner output shows it is listening for jobs.

## Phase E — configure service startup

After runner registration, from the runner installation directory:

### macOS

```bash
./svc.sh install
./svc.sh start
./svc.sh status
```

### Linux

Follow GitHub's current generated/service instructions. Depending on the platform this may require `sudo`.

Acceptance check: reboot/login behavior matches the user's intended unattended operation and `svc.sh status` reports the service running.

Important: verify that the service uses the same intended OS account / HOME / PATH as the Codex installation and authentication.

## Phase F — add the caller workflow

Create this file in the **private target repository**:

```text
.github/workflows/issue-worker.yml
```

Recommended initial contents:

```yaml
name: Issue Worker

on:
  issues:
    types: [labeled]

concurrency:
  group: issue-worker-${{ github.repository }}
  cancel-in-progress: false

jobs:
  implement:
    if: github.event.label.name == 'codex:run'
    runs-on: [self-hosted, codex]
    timeout-minutes: 60

    permissions:
      contents: write
      issues: write
      pull-requests: write

    steps:
      - name: Implement Issue with local Codex
        uses: qmore/issue-worker@main
        with:
          github-token: ${{ github.token }}
          issue-number: ${{ github.event.issue.number }}
```

If `BASE_BRANCH` is explicit, add:

```yaml
          base-branch: develop
```

Do not add `secrets: inherit` or expose unrelated repository secrets.

## Phase G — project instructions

Inspect whether `AGENTS.md` already exists.

If it exists, do not replace it blindly. Extend it only when necessary.

If it does not exist and the project has non-obvious build/coding constraints, create a concise `AGENTS.md` containing only durable repository rules such as:

```markdown
# AGENTS.md

- Build: `./scripts/build.sh`
- Test: `./scripts/test.sh`
- Do not edit generated files under `generated/`.
- Keep changes scoped to the Issue.
```

Do not put credentials or machine-specific secrets in `AGENTS.md`.

## Phase H — trigger labels

Ensure `codex:run` exists.

The action will attempt to create/update these state labels itself:

```text
codex:working
codex:review
codex:failed
codex:no-change
```

If repository policy prevents label creation from Actions, create them manually.

## Phase I — smoke test

Create a harmless Issue:

```text
Title: issue-worker smoke test

Create ISSUE_WORKER_SMOKE_TEST.md with one sentence stating that issue-worker is configured correctly. Do not modify any other files.
```

A human with write-level repository access applies `codex:run`.

Observe:

```text
Issue codex:run
  -> Actions run starts
  -> self-hosted runner receives job
  -> codex:working
  -> Codex edits workspace
  -> worker commits and pushes generated branch
  -> pull request opens
  -> codex:review
```

Check the pull request manually. Do not auto-merge the smoke test.

## Failure decision tree

### Workflow is queued

Check in order:

1. Is the runner online?
2. Does the caller repository have access to the runner scope/group?
3. Does the runner have every label in `runs-on`?
4. Is another job occupying the only runner?

Do not change to `ubuntu-latest` just to make the queue disappear; that defeats the local-environment purpose.

### Workflow starts but `codex` is missing

The service PATH differs from the interactive shell. Locate Codex:

```bash
command -v codex
```

Then fix the service/user PATH or install Codex for the service account. Do not hard-code a user-specific path in the shared Action unless there is no other option.

### Codex works in terminal but not in Actions

Compare:

```bash
whoami
printf '%s\n' "$HOME"
printf '%s\n' "$PATH"
command -v codex
```

between the interactive user and runner service context.

Likely causes:

- different HOME
- different PATH
- keychain unavailable to service session
- `CODEX_HOME` mismatch
- auth file not available to runner account

### Worker says actor is unauthorized

Do not disable the check as the first fix. Confirm the user applying `codex:run` has write-level repository access.

### Codex requests unavailable network

Prefer cached dependencies / preinstalled toolchains. If the task truly needs outbound network and the private runner is trusted, the caller may set:

```yaml
          allow-network: 'true'
```

Document why it is required.

### Generated code needs additional verification

Prefer teaching Codex the repository's normal verification in `AGENTS.md`. If a deterministic wrapper-side check is still desired, use:

```yaml
          verify-command: './scripts/verify.sh'
```

This command runs outside Codex's sandbox after Codex has modified the checkout. Treat it as trusted automation and do not use it for repositories where modified test/build scripts are untrusted.

## Completion criteria

The setup task is complete only when all are true:

- [ ] target repository is private
- [ ] Git self-hosted runner is online and visible to caller repo
- [ ] runner has `codex` label (or workflow uses the actual chosen labels)
- [ ] Codex CLI is installed in runner service PATH
- [ ] Codex non-interactive authentication works under the runner account
- [ ] caller workflow exists with minimal permissions
- [ ] workflow has a finite timeout
- [ ] `codex:run` trigger label exists
- [ ] smoke-test Issue reaches `codex:review`
- [ ] generated PR is reviewed by a human
- [ ] no credentials were copied into the repository, Issue, logs, or model-visible documentation
